2.1 Entidades Cliente, Monedero y enumeraciones

La clase Cliente representa a cada usuario individual del sistema. Almacena su UUID, nombre, correo, telefono, PIN de acceso que se valida mediante validarPin(), puntos acumulados, rango actual y colecciones internas de monederos, movimientos de puntos, alertas y canjes que se exponen como listas inmodificables. Bastante completo el cliente, la verdad.

La clase Monedero administra el saldo mediante BigDecimal redondeado a dos decimales (RoundingMode.HALF_UP). Pues el saldo solo se puede alterar mediante acreditar() y debitar(), verificando previamente que el monedero este activo y que el monto sea valido. No hay otra forma, de que no.

Las reglas fijas del negocio se definieron mediante ocho enumeraciones: RangoCliente (BRONCE, PLATA, ORO, PLATINO), TipoTransaccion, EstadoTransaccion, Frecuencia, TipoBeneficio, EstadoCanje, TipoAlerta y TipoMovimientoPuntos. Ocho en total, ni una mas ni una menos.

src/main/java/com/monedero/domain/model/Monedero.java
public void debitar(BigDecimal monto) {
    if (!activo) {
        throw new IllegalStateException("El monedero esta inactivo.");
    }
    if (monto == null || monto.compareTo(BigDecimal.ZERO) <= 0) {
        throw new MontoInvalidoException("El monto a debitar debe ser mayor que cero.");
    }
    if (this.saldo.compareTo(monto) < 0) {
        throw new SaldoInsuficienteException("Saldo insuficiente en el monedero " + nombre + ".");
    }
    this.saldo = this.saldo.subtract(monto).setScale(2, RoundingMode.HALF_UP);
}

2.2 Jerarquia de Transaccion e interfaces del dominio

Se definio la clase abstracta Transaccion que implementa la interfaz Reversible. Esta superclase concentra los atributos comunes (id, monto, fecha, estado, descripcion, sospechosa, puntosGenerados) y declara los metodos abstractos ejecutar(), revertir(), obtenerTipo(), obtenerClientePrincipal() e involucraCliente(UUID). Todo bien definido desde arriba, pues.

De Transaccion heredan tres subclases concretas: Deposito, Retiro y Transferencia. Cada una implementa su propia logica de ejecucion y de reversion. Ademas se crearon las interfaces CalculadorPuntos y Notificable para desacoplar la puntuacion y el envio de alertas. Se crearon, se crearon y ya.

public abstract class Transaccion implements Reversible {

    private final BigDecimal monto;

public static BigDecimal parsearMontoPositivo(String texto) {
    if (texto == null || texto.trim().isEmpty()) {
        throw new MontoInvalidoException("Debe ingresar un monto.");
    }
    try {
        BigDecimal valor = new BigDecimal(texto.trim().replace(",", "."));
        if (valor.compareTo(BigDecimal.ZERO) <= 0) {
            throw new MontoInvalidoException("El monto debe ser mayor que cero.");
        }
        return valor;
    } catch (NumberFormatException e) {
        throw new MontoInvalidoException("El formato del monto no es valido.");
    }
}

3.1 Repositorios en memoria con LinkedHashMap y Optional

La persistencia se abstrajo mediante cinco interfaces en com.monedero.repository (ClienteRepository, MonederoRepository, TransaccionRepository, BeneficioRepository y ProgramadaRepository) y sus respectivas implementaciones en com.monedero.repository.memory. Cinco interfaces, cinco implementaciones, todo cuadrado.

Cada implementacion en memoria utiliza un LinkedHashMap indexado por UUID para preservar el orden de insercion con busqueda directa y retorna Optional en las consultas por identificador. La verdad, cada implementacion sigue el mismo patron, que no es casualidad.

src/main/java/com/monedero/repository/memory/InMemoryTransaccionRepository.java
public class InMemoryTransaccionRepository implements TransaccionRepository {
    private final Map<UUID, Transaccion> datos = new LinkedHashMap<>();

    @Override
    public Optional<Transaccion> buscarPorId(UUID id) {
        return Optional.ofNullable(datos.get(id));
    }

    @Override
    public List<Transaccion> obtenerPorCliente(UUID clienteId) {
        return datos.values().stream()
                .filter(t -> t.involucraCliente(clienteId))
                .collect(Collectors.toList());
    }
}

3.2 Autenticacion individual y gestion de monederos

ClienteService gestiona el registro de nuevas cuentas verificando correo unico y la autenticacion individual por correo y PIN en autenticar(correo, pin). Cada cuenta registrada inicia con un monedero principal activo. Pues asi de simple.

MonederoService permite a cada cliente autenticado crear multiples monederos propios (por ejemplo Principal, Ahorros o Gastos), consultar el saldo total consolidado y activar o desactivar cada monedero de forma independiente. Se puede tener varios, la verdad es que si.

src/main/java/com/monedero/service/ClienteService.java
public Cliente autenticar(String correo, String pin) {
    Validaciones.validarTextoNoVacio(correo, "correo");
    Validaciones.validarTextoNoVacio(pin, "PIN");
    String correoBuscado = correo.trim().toLowerCase();

    Cliente cliente = clienteRepository.obtenerTodos().stream()
            .filter(c -> c.getCorreo().trim().toLowerCase().equals(correoBuscado))
            .findFirst()
            .orElseThrow(() -> new EntidadNoEncontradaException("No existe una cuenta con ese correo."));

    if (!cliente.validarPin(pin)) {
        throw new IllegalArgumentException("El PIN ingresado es incorrecto.");
    }
    return cliente;
}

3.3 Operaciones financieras y transferencias entre monederos propios

TransaccionService coordina depositos, retiros, transferencias y reversiones. Tras ejecutar la operacion y persistirla, actualiza puntos, ejecuta la deteccion de transacciones atipicas y verifica de que el saldo descendio del umbral de alerta ($50.00). De que si, de que si.

Los retiros aplican una comision base del 1% y las transferencias hacia terceros una comision base del 2%, ajustadas segun el rango y beneficios del cliente. Cuando el monedero de origen y destino pertenecen al mismo propietario, la comision se establece en BigDecimal.ZERO ($0.00). La funcion revertirTransaccion() revierte tanto los fondos como los puntos generados. O sea, todo vuelve como estaba.

src/main/java/com/monedero/service/TransaccionService.java
public Transferencia transferir(UUID origenId, UUID destinoId, BigDecimal monto, String descripcion) {
    Monedero origen = monederoService.buscarPorId(origenId);
    Monedero destino = monederoService.buscarPorId(destinoId);
    boolean entrePropios = origen.getPropietario() != null
            && destino.getPropietario() != null
            && origen.getPropietario().getId().equals(destino.getPropietario().getId());
    BigDecimal comision = entrePropios
            ? BigDecimal.ZERO
            : calcularComisionTransferencia(origen.getPropietario(), monto);
    Transferencia transferencia = new Transferencia(origen, destino, monto, comision, descripcion);
    transferencia.ejecutar();
    transaccionRepository.guardar(transferencia);
    puntosService.registrarPuntosPorTransaccion(transferencia);
    deteccionAtipicasService.analizarYAlertar(transferencia);
    verificarSaldoBajo(origen);
    return transferencia;
}

3.4 Sistema de puntos, rangos y canje de beneficios

PuntosService implementa CalculadorPuntos otorgando puntos por cada bloque completo de 100 unidades: 1 punto en depositos, 2 en retiros y 3 en transferencias, mas la bonificacion porcentual del rango actual del cliente. Al acumular o revertir puntos, el cliente recalcula automaticamente su RangoCliente (BRONCE, PLATA, ORO o PLATINO). Se recalcula solo, o sea, sin que uno haga nada.

BeneficioService valida la disponibilidad del beneficio y los puntos del cliente antes de registrar el canje en CanjeBeneficio. Si el beneficio es de tipo BONO_SALDO, acredita automaticamente el valor en el monedero activo del usuario. Pues eso, que el saldo sube sin que uno mueva un dedo.

src/main/java/com/monedero/service/PuntosService.java
int bloques = transaccion.getMonto().divideToIntegralValue(BLOQUE_PUNTOS).intValue();
int tasa = (tipo == TipoTransaccion.DEPOSITO) ? 1
        : (tipo == TipoTransaccion.RETIRO) ? 2 : 3;
int puntosBase = bloques * tasa;
Cliente cliente = transaccion.obtenerClientePrincipal();
if (cliente != null && puntosBase > 0) {
    double bono = cliente.getRango().getBonoPuntos();
    puntosBase += (int) Math.floor(puntosBase * bono);
}

4.1 Transacciones programadas con ordenamiento por insercion

TransaccionProgramada modela operaciones unicas o recurrentes (DIARIA, SEMANAL, MENSUAL). En ProgramacionService.obtenerOrdenadasPorFecha() se implemento el algoritmo de ordenamiento por insercion (Insertion Sort) comparando la fecha de proxima ejecucion. Un algoritmo clasico, la verdad, de los que uno ve en clase.

El metodo ejecutarPendientes() procesa en orden cronologico las operaciones cuya fecha ya se cumplio y emite alertas locales ante ejecuciones exitosas o fallidas. Pues eso, que avisa cuando algo sale bien y cuando sale mal.

src/main/java/com/monedero/service/ProgramacionService.java
public List<TransaccionProgramada> obtenerOrdenadasPorFecha() {
    List<TransaccionProgramada> lista = new ArrayList<>(programadaRepository.obtenerActivas());
    for (int i = 1; i < lista.size(); i++) {
        TransaccionProgramada actual = lista.get(i);
        int j = i - 1;
        while (j >= 0 && lista.get(j).getProximaEjecucion().isAfter(actual.getProximaEjecucion())) {
            lista.set(j + 1, lista.get(j));
            j--;
        }
        lista.set(j + 1, actual);
    }
    return lista;
}

4.2 Analisis de patrones de gasto con Stream API

AnalisisGastosService procesa las transacciones completadas mediante Stream API y colectores (groupingBy, reducing) para calcular ingresos totales, gastos totales, egresos agrupados por tipo y las operaciones de mayor valor. Se procesa, se agrupa, se reduce, todo con la misma API.

Los metodos esIngresoParaCliente() y esGastoParaCliente() excluyen las transferencias internas realizadas entre monederos del mismo titular para no distorsionar las metricas reales de ingreso o gasto. La verdad es que si no las excluyeran, las cuentas saldrian mal.

src/main/java/com/monedero/service/AnalisisGastosService.java
public Map<TipoTransaccion, BigDecimal> agruparGastosPorTipo(UUID clienteId) {
    return transaccionRepository.obtenerPorCliente(clienteId).stream()
            .filter(t -> t.getEstado() == EstadoTransaccion.COMPLETADA)
            .filter(t -> esGastoParaCliente(t, clienteId))
            .collect(Collectors.groupingBy(
                    Transaccion::obtenerTipo,
                    LinkedHashMap::new,
                    Collectors.reducing(BigDecimal.ZERO, Transaccion::getMonto, BigDecimal::add)
            ));
}

4.3 Deteccion de transacciones atipicas y alertas locales

DeteccionAtipicasService evalua cada movimiento cuando el cliente posee al menos tres transacciones completadas previas. Calcula el promedio historico y la desviacion estandar poblacional en tiempo O(n) para obtener el umbral promedio + 2 * desviacion. Pues eso, puro calculo estadistico.

Cuando una transaccion supera ese umbral, se marca como sospechosa y NotificacionService registra una alerta local de tipo TRANSACCION_ATIPICA en el historial del cliente. Se marca, se registra, se avisa, todo en orden.

src/main/java/com/monedero/service/DeteccionAtipicasService.java
public double calcularDesviacionEstandar(List<Double> montos, double promedio) {
    if (montos == null || montos.isEmpty()) {
        return 0.0;
    }
    double sumaCuadrados = montos.stream()
            .mapToDouble(m -> Math.pow(m - promedio, 2))
            .sum();
    return Math.sqrt(sumaCuadrados / montos.size());
}

public double calcularUmbral(List<Double> montos) {
    double promedio = calcularPromedio(montos);
    double desviacion = calcularDesviacionEstandar(montos, promedio);
    return promedio + (2.0 * desviacion);
}

1. Pasos del pensamiento computacional

1. Abstraccion

Bueno, consistio en identificar los elementos esenciales del problema del monedero virtual y descartar los detalles tecnicos ajenos al alcance academico (como pasarelas bancarias externas o servidores remotos). La verdad es que fue cuestion de quedarse con lo importante.

  • Se abstrajo a cada usuario en la clase Cliente con credenciales de acceso (correo y PIN), puntos acumulados, rango actual y sus colecciones asociadas.
  • Las cuentas del cliente se modelaron mediante Monedero con saldo decimal exacto (BigDecimal) y estado activo/inactivo.
  • Depositos, retiros y transferencias se unificaron bajo la abstraccion comun Transaccion con monto, fecha, estado y operaciones de ejecucion y reversion.

2. Descomposicion

El sistema se dividio en capas y modulos independientes para resolver cada requerimiento por separado y facilitar su mantenimiento y prueba. Se dividio, se dividio, y quedo bien dividido.

  • Separacion estructural en paquetes: app, domain (model, interfaces, exception), repository, service, controller y util.
  • Division de la logica de negocio en servicios especializados: ClienteService, MonederoService, TransaccionService, PuntosService, BeneficioService, ProgramacionService, AnalisisGastosService, DeteccionAtipicasService, NotificacionService y TareaService.
  • Division de la interfaz grafica en nueve archivos FXML independientes, asignando cada funcionalidad solicitada a su propia vista y controlador.

3. Reconocimiento de patrones

Se identificaron comportamientos repetitivos en el manejo de datos y flujos de operacion para resolverlos mediante estructuras reutilizables. Pues eso, ver que se repite y reutilizarlo.

  • Patron de persistencia uniforme: los cinco repositorios en memoria replican la misma estructura basada en LinkedHashMap<UUID, Entidad> y retorno Optional<T>.
  • Patron de ciclo financiero: toda operacion monetaria sigue la secuencia validacion -> ejecucion -> registro -> calculo de puntos -> analisis de atipicidad.
  • Patron de refresco en interfaz: AppContext centraliza una accion de actualizacion para refrescar el encabezado de usuario, rango y puntos tras cualquier operacion.

4. Codificacion

Traduccion del diseno y los algoritmos definidos a codigo Java 21 compilado con Maven, JavaFX y validado mediante pruebas unitarias JUnit 5. Se codifico, se compilo, se probo. Todo el ciclo.

2. Encapsulamiento

Se protegio el estado interno de las entidades declarando atributos privados y restringiendo cualquier modificacion a metodos con reglas de validacion. La verdad es que sin esto el codigo seria un caos.

  • En Monedero, el atributo saldo es private y no posee metodo setSaldo(); solo cambia a traves de acreditar() y debitar() luego de validar estado activo, monto positivo y saldo suficiente.
  • En Cliente, el PIN es privado y se verifica exclusivamente mediante validarPin() sin exponerlo al exterior.
  • Las listas internas de Cliente (monederos, historialPuntos, alertas y canjes) se exponen mediante Collections.unmodifiableList() para impedir alteraciones directas fuera de la clase.

private final List<Monedero> monederos = new ArrayList<>();

public boolean validarPin(String intento) {
    return intento != null && this.pin.equals(intento.trim());
}

public List<Monedero> obtenerMonederos() {
    return Collections.unmodifiableList(monederos);
}

3. Herencia

Permitio reutilizar atributos, validaciones y comportamiento comun mediante especializacion de clases padre hacia clases hijas. Se hereda, se hereda, y se ahorra codigo.

  • Deposito, Retiro y Transferencia extienden la clase abstracta Transaccion, heredando el identificador UUID, el monto escalado a dos decimales, la fecha, el estado, la descripcion, el indicador sospechosa y los puntos generados.
  • Las excepciones de negocio (SaldoInsuficienteException, PuntosInsuficientesException, MontoInvalidoException y EntidadNoEncontradaException) heredan de RuntimeException para integrarse de manera uniforme en el manejo de errores.
src/main/java/com/monedero/domain/model/Deposito.java
public class Deposito extends Transaccion {
    private final Monedero monederoDestino;

    public Deposito(Monedero monederoDestino, BigDecimal monto, String descripcion) {
        super(monto, descripcion);
        if (monederoDestino == null) {
            throw new IllegalArgumentException("El monedero destino es obligatorio.");
        }
        this.monederoDestino = monederoDestino;
    }
}
